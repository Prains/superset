## Overview

A plugin is a directory with a `superset-plugin.json` manifest plus up to two entries: a backend that runs in-process inside the host-service on the machine that owns your workspaces, and a UI bundle whose React components render in native slots of the desktop app (right-sidebar tabs, panes, command palette). One package can serve a panel for humans and actions/events for the system at the same time.

<Callout type="warn" title="Trust model">
Plugins are full-trust code, the same class as `.superset/config.json` setup scripts. There is no sandbox. There is containment: every handler is time-boxed and error-contained, a plugin that throws at load lands as `status: error` without affecting other plugins or the host, and UI slots are wrapped in error boundaries. Only install plugins from authors you trust, and read the manifest (including `permissions`) before installing.
</Callout>

## Installing and Managing Plugins

### In the app

Open **Plugins** from the dashboard sidebar. The **Browse** tab lists community plugins from the `superset-plugin` GitHub topic with one-click install. The page lists installed plugins with their status and lets you enable, disable, reload, or uninstall each one. Install new plugins from a GitHub `owner/repo` shorthand, a git URL, or a local path (local paths are dev-linked, so the plugin runs from your directory in place).

Click any plugin for its detail page: what it adds (commands, panes, sidebar tabs, event hooks), where each surface appears, declared permissions, and source provenance.

**Build with AI** dispatches an agent session that scaffolds, implements, and links a plugin from a one-line description. The agent uses the bundled `plugin-authoring` skill, so it knows the manifest, the SDK, and the verification loop.

### From the CLI

```bash
superset plugin install owner/repo             # git clone (GitHub shorthand)
superset plugin install owner/repo --ref v1.2  # pinned to a tag/branch, commit recorded
superset plugin install ./some-dir             # copy into ~/.superset/plugins/<id>
superset plugin link .                         # dev: run from the directory in place
superset plugin list                           # every plugin with status + load errors
superset plugin enable <id>
superset plugin disable <id>
superset plugin reload <id>
superset plugin uninstall <id>
```

Install shows a preview (id, version, permissions, contribution counts) before anything runs. The app picks up install/enable/disable/reload within about 2 seconds, no restart needed. Plugin state and storage live in the host database and survive app and host restarts. `uninstall` removes the managed copy, but a linked directory is never deleted.

## What Plugins Can Extend

| Contribution | What it does | Runs code? |
|--------------|--------------|------------|
| `sidebarTabs` | A tab in the workspace right sidebar, next to Files/Changes/Review | UI |
| `panes` | A full pane kind in the workspace pane grid (splittable, persists in the layout) | UI |
| `commands` | Command-palette entries that invoke a backend action, open a sidebar tab, or open a pane | Backend / none |
| `events` | Spawn a command on a lifecycle event, with `SUPERSET_PLUGIN_*` env context. No backend needed | Child process |
| `themes` | Reserved (not wired yet) | None |

## Building Your First Plugin

```bash
superset plugin new my-plugin   # scaffold: manifest + server.ts + app.tsx
cd my-plugin
superset plugin build .         # esbuild the UI bundle into dist/app.js
superset plugin link .          # register the directory in place (dev mode)
```

Open any v2 workspace: your sidebar tab appears next to Files/Changes/Review and your commands appear in the command palette. Iterate with `superset plugin build .` and `superset plugin reload <id>`.

The full authoring guide, with the complete manifest reference, backend and UI APIs, and runnable examples, lives at [Building Plugins](/building-plugins).

## Current Limits

- UI slots today: right-sidebar tabs, pane kinds, palette commands. File views, settings pages, and keybindings are not wired yet
- `permissions` are declared and shown at install, not yet enforced; the backend runs with the host-service's full capability
- The SDK is 0.x: contracts may change until the first tagged release
